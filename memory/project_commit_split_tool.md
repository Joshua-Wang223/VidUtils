## 事实

`test/split_diff_by_theme.py`（2026-09-23 入库）解决的是**分提交时的 hunk 手术**：

- 输入：`git diff`（默认工作区 vs 索引；`--rev R` 可换基线）+ 一份**规则 JSON**；
- 输出：**只出 A 侧补丁**（`git apply --cached --recount a.patch` → 提交 A → `git add <files>`
  → 提交 B）。B 侧不需要单独生成 —— 它就是"工作区减去已提交的 A"，由 `git add` 自然得到；
  反过来先造"对着 HEAD 的 B 补丁"再在 A 之后应用必然冲突。
- 判定顺序：**① 整块覆盖（whole_block）→ ② 逐行规则（mixed_block）→ ③ 关键词 → ④ 沿用上一段**；
  判不出来的一律标 `?` 并打告警，**绝不静默分错线**。
- 两种自证：`--verify`（在**临时索引**上应用 A，再把"索引↔工作区"的差当 B 应用，最后逐文件
  比对 blob == 工作区；不碰真实索引）、`--selftest`（在 `temp/` 建临时仓库造两条线，
  逐字节断言 A 的结果 + 无损性 + 告警的正负格）。

## Why

这条线在 2026-09-22/23 手工做过一次（色度线 + 码率控制线拆成两条提交）：当时是现写的
一次性脚本，靠人肉核对 hunk 分类；**同一个动作在这个项目里会反复出现**（README/memory 这类
"两个主题都改过"的文件是常态），而手写 patch 的坑又特别多。固化后：分类规则可复核、
无损性有机器判据、坑写进了自证。

## ⭐ 自证当场抓到的四个真 bug（都不是被测对象的问题，而是拆分器自己）

| # | 症状 | 根因 | 判据 |
|---|---|---|---|
| 1 | 一个段落都没分出来 | `Hunk` 在**行还没填进 `lines` 之前**就建好了段落（解析器先建空 Hunk 再追加行） | `--selftest` 第一条断言 |
| 2 | 两条线的新增行被整块判给一侧 | 两线增行**相邻**时 git 只给**一个**变更组；逐行规则里"无关键词的续行"必须**沿用上一行**（函数体/空行/注释续行都没有关键词） | A 侧结果 == 期望文本 |
| 3 | B 的替换组（`-return 2`/`+return 3`）被算进 A | 无关键词的替换组按"沿用上一段"猜错了 —— 改成**显式标 `?` + 按 default**，并加"补上规则后告警必须消失"的正向格 | 告警存在 / 规则补齐后告警消失 |
| 4 | `patch does not apply`、`diff` 与 git 自己的不一致 | `@@` 头重算时**丢了换行**（`@@` 行与下一行粘连）、**两侧计数少算**（上下文段被拼成一坨只算 1 行）。⚠ 这两个 bug 被 `git apply --recount` **掩盖**了（recount 会重算计数），只有"与 `git diff` 逐字节对比"才暴露 | 单主题时"我的补丁 == `git diff <base> <commit>`"|

## How to apply

- 需要拆提交时**先用工具、别手写 patch**：
  `--print-rules > rules.json`（改 files / 关键词 / 覆盖规则）→ `--report` 看分类 →
  `--out … --verify` 出补丁并自证。
- **验收判据（三条，缺一不可）**：
  1. `--selftest` 全绿；
  2. `--verify` 报「A + 剩余 == 工作区」；
  3. **单主题对照**：规则的 A 侧覆盖全部改动时，输出补丁应与 `git diff <base> <commit>`
     **逐字节相同**（这条能抓住 `@@` 头/计数类的 bug，是 `--recount` 掩盖不了的那类）。
- 报告里出现 `[X?]` 或告警时**必须人工看那一段**（例：无关键词的替换组、同时命中两线
  关键词的组）——给规则加 `whole_block` / `mixed_block` 直到告警清零。
- ⚠ 变更组是**原子**的：`-旧`/`+新` 必须同侧，否则 A 那次提交会"删了旧的、没加新的"直接编译不过。
- ⚠ 写这类工具/夹具时，**别用 bash heredoc 传含反斜杠的 Python 代码**（本轮实测：`\\n` 被折叠成真换行，
  把文件里的正则与 f-string 写坏）→ 用 Edit 工具写文件内容。
