 The user asked a question back: "哪种方式并行性能更优其稳定？" (which approach has better parallel performance and stability?)
 I should answer that. In bash, parallelism = background subshells + wait. In Python, ThreadPoolExecutor + subprocess — actually the bottleneck is ffprobe
 subprocesses, so both are I/O-bound concurrent process spawning. Python's ThreadPoolExecutor is easier to bound, collect results deterministically, handle timeouts,
 and avoid the repo's documented bash pitfalls (wait -n early return, tail<() hang, orphan processes — see project_bash_parallel_pitfalls.md). Also JSON parsing in
 Python avoids fragile key=value parsing. Performance is essentially identical since both just spawn N ffprobe processes; the concurrency limit matters more than the
 language.
 So recommendation: Python core for the parallel probing + JSON parsing; but named vidls.sh? They asked for vidls.sh. Hmm — a .sh wrapper calling vidls.py is a bit odd
 since repo is python-native. But user explicitly wanted `vidls.sh` + PATH entry.

● Direct answer to your question: for parallel stability, Python wins; throughput is a tie.

  - Both approaches just spawn N concurrent ffprobe processes, so wall-clock is the same — the bottleneck is the concurrency limit, not the language.
  - But this repo already has a memory file (memory/project_bash_parallel_pitfalls.md) documenting four bash scheduling traps they hit: wait -n returning early, while 
  read < <(tail) hanging forever, orphan processes from subshells, and fragile instance matching. Reproducing a correct bounded pool in bash means re-solving those.
  - Python's ThreadPoolExecutor + subprocess.run(timeout=...) gives deterministic result collection, per-file timeouts, and json.loads instead of fragile key=value
  scraping.

  So: vidls.sh as a thin launcher + vidls.py as the engine. Let me delegate the riskiest design piece (faithfully reimplementing ls layout) while I nail down the rest.
