做「中间产物 + 最终替换」的设计时，两个自己踩的坑。都不在业务逻辑里，
但都让「本来正常的功能」看起来是坏的。

## 坑一：中间产物残留但没人告知

给 `--subs keep` 加两阶段（先编码 → `-c copy` remux 挂字幕）后，实测 remux 失败时：

```
阶段1 存在: True 大小 96122
rc= 234 | Stream map '' matches no streams.
★ 失败后：阶段1 还在吗? True
★ 最终路径上有文件吗? False
```

**最终路径上没有文件是对的**（不会误交付「看起来正常其实缺字幕」的成品）。
但阶段1 那 96KB 文件**留在输出目录且无任何提示** ⇒ 用户看到「转完了文件却不见了」，
还会以为是自己删错了。

⇒ 修法：`except` 里若阶段1 仍存在就 `job.warnings.append(f"阶段1 产物已保留在 {…}
（可用，只是没挂字幕）")`。**不清理是故意的**（那个文件是可用的），但**必须说**。

同型：burn 导出的字幕临时目录 `.subs_burn/` 原本**从不清理** ⇒
批量跑一遍会在**每个输出目录**留一堆 `.srt`。已挂在 `finally` 清理
（只删自己导出的那一个 + 空目录）。

**Why:** 这两处属于「产物层面的静默失效」—— 退出码与门禁全绿（remux 失败时
退出码确实是 1，但**残留文件本身没人报**）。

**How to apply:** 任何「中间产物 + 最终替换」的设计，枚举**每一条失败路径**并回答：
①最终路径上会不会留下半成品？②中间产物会不会残留？③两者要不要提示？
只验成功路径不够。

## 坑二：`finally` 里引用外层作用域不存在的变量

给 burn 加清理时我写在 `run_job` 的 `finally` 里：

```python
if st.subs_burn_file:      # ❌ run_job 里没有 st（它在 plan["settings"]）
```

⇒ `NameError` 把**整个转换**搞失败（EXIT=1、目录还在），而编码主逻辑本身是好的。
我第一次跑就撞上了（EXIT=1 且 `.subs_burn` 还在）。

**Why:** `finally` 里的清理看起来是「收尾」，直觉上不会影响主流程；但异常会从
`finally` 抛出并**替换掉**原有的返回值 ⇒ 一个「清理 bug」的破坏力可以远大于它本身。

**How to apply:**
- 在 `finally`/`except` 里引用变量前，确认它在本函数作用域内存在；
  不确定就用 `locals()` 或显式传参（本次改成 `plan.get("settings").subs_burn_file`）。
- **整段包 `try/except Exception: pass`** —— 连引用本身也要在保护内。
- 原则：**清理失败不该影响转换结果**。
- 同型：跨分支共享的标志必须在函数开头**显式初始化**，不能指望「走到那里就赋值了」
  （本次另一个坑：`-i src 是否已加入` 的标志只在有音频的分支里赋值）。

## 附：抄别处的代码会抄错函数名

复刻判据时我把 benchmark 脚本的 `_to_int` 写进了被测脚本 ⇒ `NameError`
（本脚本用 `_frac_to_float`，没有 `_to_int`）。⇒ 跨脚本复制代码后，
先 `grep -c 'def <函数名>'` 确认目标文件里真有它。
