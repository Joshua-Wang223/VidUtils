2026-10-09 用户要求给 `convert_sdr_to_hdr.py` 的字幕 burn 加一条：
「为防止**重复解码编码**造成视频质量下降，中间编码（burn 字幕前）应适当提高编码
质量，如 crf/cq/qp 自动提高 1-2 级」。

我实测发现该要求的两条前提都不成立，于是**没有照做**，而是把证据摆出来让用户在
两个方案间选：

1. **不存在中间编码**：`subtitles` 滤镜能直接吃脚本的中间格式 `gbrp16le`，
   实测 rc=0 ⇒ burn 仍是「解码→NN 推理→**一次**编码」，没有「重复编码」可言。
2. **烧字幕的码率代价只有 1%**：同 crf 下 194KB→196KB（crf 26/25/24 三档一致）。
   提质 1-2 级会让体积涨 15-30%，属过度补偿。

**用户的选择：A（不加提质，burn 保持单次编码）。** ✅ 这条闭环验证了
「先验证前提再让用户定」的做法有效——用户接受反证、选了更省的方案，
而不是要求我按字面实现。

**Why:** 用户提这条要求显然是**为了保护画质**（动机是对的），只是基于「burn 需要
两次编码」这一错误前提。按字面实现（自动降 crf）会付出真实的体积代价却换不来
任何画质收益——因为不存在第二次编码。

**How to apply:**
- 用户给出带**因果假设**的技术要求（「为防 X，所以要 Y」）时，先花几步实测
  验证 X 是否真的存在；前提不成立时，**明确说「实测证明 X 不成立」并给数据**，
  再给替代方案让他选。
- 区别于「拒绝用户要求」：这里仍实现了用户真正想要的目标（burn 保画质），
  只是用**更省的方式**达成，并让用户知道取舍不同在哪。
- 询问要给**可选项 + 每项的实测代价**（本例：A 不加提质保持单次编码 /
  B 加默认 0 的提质旋钮留余量），而不是开放式提问「你觉得怎么办」。
- ✅ 后续同一次任务里，用户又基于我的实测数据追加了第二个决策
  （keep 分情况：只在会触发 ffmpeg bug 时才走两阶段）——再次接受「按实测条件
  分支」的做法。**连续两轮都验证了：把取舍连同实测数字摆出来让用户定，
  比自行替用户决定默认行为更受欢迎。**
- ⚠ 关联 `feedback_conservative_fix_default_behavior.md`（用户偏好保守修法 +
  告警）：那条讲「改默认行为要先问」，本条讲「要求的技术前提要先验证」。
  两者都是「不盲目执行、但也不擅自否决」。
