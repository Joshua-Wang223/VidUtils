# Bug B3：编码器收尾（flush）被固定超时误杀 —— librav1e 类慢速编码器无产物失败

- 发现日期：2026-10-14
- 现象：`--codec librav1e` 跑 30 帧，`汇总: 完成 0 失败 1`，`编码 ffmpeg 退出码 -9`，
  伴随告警「编码器 120s 未退出，已强制终止（末帧收尾卡住）」；产物仅 48 字节。
- 影响面：任何**慢速编码器 + 长收尾**的组合。原 4 核机 L1 里 librav1e 是**最快**软编
  （292s），到 ffmpeg 9.0.2 上却成了唯一失败项 —— 纯环境差异触发。

## 一、根因（与 av1_nvenc 的收尾卡死**不同源**，此前判断有误已纠正）

**不是死锁，是固定超时预算估错了。**

实测（720p / 30 帧 / `-qp 64` / yuv420p10le，ffmpeg 9.0.2）：

| 场景 | 耗时 | 备注 |
|------|------|------|
| 裸 ffmpeg，30 帧从**文件**喂入 | **2m30s** 完成出片 | 单次跑通，非死锁 |
| 裸 ffmpeg，同命令 `-threads 1` vs `-threads 24` | 2m32s vs 2m30s | librav1e 单线程，`-threads` 无影响 |
| 走脚本管道 | 帧循环 **1m41s** → stdin EOF 后 flush **~4m** | 合计 4m33s |
| 首次尝试（自适应 3× 帧循环） | 312s 预算 → 仍被 `-9` | flush 实际 ~364s，**差一点** |

关键：**flush 耗时与帧循环耗时没有固定比例**（此例 3.5×，且会随编码器/分辨率/内容变化）。
原代码 `enc.wait(timeout=120)` 是 B2 为 av1_nvenc 加的**固定预算**，对 librav1e 变成误杀。

> 纠正：上一轮 memory/方案里写的「librav1e 与 av1_nvenc 收尾卡死同源」**是错的**。
> 若真同源，B2 的排空 `dec.stdout` 就该治好 librav1e —— 它没有。
> av1_nvenc 是**零推进的真死锁**，librav1e 是**持续推进的慢 flush**。

## 二、为什么「加长超时」不是根治

第一次尝试即自适应超时 `3 × 帧循环耗时`（下限 120s / 上限 3600s）——**仍失败**：
实测 flush 是帧循环的 3.5×，公式猜小了。这暴露了固定预算的**原理缺陷**：

> 固定总预算无法区分「慢但正常推进」与「真卡死不动」。
> 猜小 → 误杀正常编码的慢编码器（本例，且**无产物**，是可用性事故）；
> 猜大 → 真卡死时要多等数小时。

## 三、根治方案：按「无推进时长」判定（liveness-based）

判据从「总耗时」改为「**连续多久没有任何推进**」，数据源是 ffmpeg 自身的 `-progress` 心跳。

1. **编码命令下发心跳**：`-stats_period 2 -progress pipe:2`
   （走 stderr，与既有排空线程同一通道，不新增管道）

2. **`_spawn_stderr_drain(..., on_heartbeat=cb)`**：识别 `_PROGRESS_KEY_RE`
   （`frame=` / `out_time_us=` / `progress=` 等 key=value 行）→ 回调刷新心跳时间戳，
   并**不写进诊断 sink**（否则心跳会挤掉真正的错误行，破坏既有报错可读性）。

3. **`_wait_enc_flush(enc, args, job, frames_elapsed, hb)`**：替代固定 `enc.wait(timeout=N)`：
   - 每 2s 轮询一次进程状态
   - `now - max(最后心跳, flush 起点) > --enc-stall`（默认 **180s**）⇒ 判定卡死 → `_terminate`
   - `--enc-timeout`（0=自适应，上限 3600s）降级为**纯兜底上限**，不再是主要判据
   - 心跳一条都没收到过（老 ffmpeg / 启动即卡）时以 flush 起点为基准，不会立即误杀

**同时修掉同类隐患**：`run_job_multiproc`（workers 多进程路径）原本是**完全无超时**的
`enc.wait()` / `dec.wait()`，同一处一并改为看门狗 + `dec.wait(timeout=10)`。

## 四、验证

| 用例 | 期望 | 实测 |
|------|------|------|
| **单测**：假编码器 flush 后永久静默挂住 | 判卡死并终止 | 180.0s 判定，`rc=-15`，告警文案正确 |
| **单测**：假编码器每 2s 发心跳共 80s | 绝不被误杀 | 79.9s 正常退出 `rc=0` |
| **单测**：心跳行是否污染诊断 sink | 不污染 | `sink=[]`（心跳被正确过滤） |
| **端到端** librav1e 30 帧 | 成功出片 | ✅ 完成 1 失败 0，4m33s，415033 bytes，`av1/yuv420p10le/smpte2084/bt2020` |
| **回归** libx265 30 帧 | 不受影响 | ✅ 1m43s |
| **回归** libaom-av1 30 帧 | 不受影响 | ✅ 5m06s |
| **回归** `verify_sdr_to_hdr.py` 八项（含逐字断言命令 token 顺序） | 全通过 | ✓ 全部通过 |

> 注：`-progress`/`-stats_period` 加在输出路径**之前**，`verify_sdr_to_hdr` ③ 的
> `shlex.split(cmd)[-3:]` token 顺序契约不受影响（已实测通过）。

## 五、新增 CLI

```
--enc-stall SEC     收尾期「连续无推进」多少秒判卡死。0=自动 180s
--enc-timeout SEC   总预算上限，仅兜底。0=自动（6×帧循环，下限 300s，上限 3600s）
```

默认无需设置。**不建议**用 `--enc-timeout` 调大来「解决」慢编码器 —— 那是在猜。

## 六、遗留

- **av1_nvenc 的真死锁本轮未在本机复现**（无 GPU）。它的零推进特征现在会被 `--enc-stall`
  在 180s 内捕获，不再需要靠固定总预算。GPU 阶段应专门回归一次：确认告警文案变为
  「N s 无任何推进，已强制终止（末帧收尾卡死）」而非旧的「未退出」。
